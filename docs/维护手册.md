## 1. ⛔ 三条运维红线（先读这一节）

| # | 红线 | 说明 |
| --- | --- | --- |
| **1** | **生产库（prod）的数据永远不可删除** | 不清空、不重置、不用空数据 `import --prod --replace`、不删光表里的行。要移除**具体记录**就用业务操作或按 id 定向删除。`reset-data.sh --prod` 已被脚本默认拒绝；`purge-except.mjs` 需 `ALLOW_PURGE=1` |

| **3** | **任何导出物都含敏感数据** | `backups/` 里有 `sessions` 表的**明文 bearer token** 与成员邮箱，而本仓库是 **public**。`backups/`、`snapshots/`、`.import-tmp.json`、`.env.local` **必须保持 gitignore** |

> 这三条对应 `AGENTS.md` 顶部、§2、§12、§13。下面每个危险操作都会重复标注。

## 3. 本地安装与运行

```bash
git clone git@github.com:lshengjian/my_kanban.git
cd my_kanban
npm install
```

### 3.1 准备环境变量

```bash
cp .env.local.example .env.local
```

`.env.local` 需要 `CONVEX_DEPLOYMENT`、`VITE_CONVEX_URL`、`VITE_CONVEX_SITE_URL`
（**后两个客户端已不读取**，仅 `scripts/project-snapshot.mjs` 用作 sanity gate —— 见 §4）。

### 3.2 起后端（独立进程）

```bash
npx convex dev          # 常驻，监听 convex/ 变更并推送 dev deployment
```

### 3.3 起前端（另一个终端）

```bash
npm run dev             # Vite → http://127.0.0.1:5173
```

### 3.4 可用脚本

| 命令 | 作用 |
| --- | --- |
| `npm run dev` | Vite 开发服务器 |
| `npm run typecheck` | `tsc --noEmit`（前后端一次校验） |
| `npm run build` | `tsc --noEmit && vite build` → `dist/` |
| `npm run preview` | 预览 `dist/` |
| `npx convex dev` | 起 Convex 后端（无对应 npm script） |
| `npx convex dev --once` | 推一次 dev 后退出（适合脚本/CI） |

## 4. 配置说明

### 4.1 两个 Convex deployment

| | 开发测试环境 (dev) | 生产环境 (prod) |
| --- | --- | --- |
| deployment | `lsj1788:kanban:kanban-dev` | `lsj1788:kanban:production` |
| URL | `https://fine-ibis-920.convex.cloud` | `https://coordinated-camel-303.convex.cloud` |
| 选它的命令 | 默认（`.env.local`） | 加 `--prod` |
| 账号体系 | **与 prod 完全独立** | **与 dev 完全独立** |

两者是**两个独立数据库**：账号、项目、会话都不互通。前端在登录页提供「后端数据」切换器。

### 4.2 前端的后端地址从哪来

`src/backend.ts` 的 `BACKENDS[env].url` 是**唯一来源**，可被覆盖：

```bash
VITE_CONVEX_URL_PROD=https://...   # 覆盖 prod
VITE_CONVEX_URL_DEV=https://...    # 覆盖 dev
```

默认环境是 **prod**（`DEFAULT_ENV = "prod"`）。

> ⚠️ `.env.local` 里的 `VITE_CONVEX_URL` / `VITE_CONVEX_SITE_URL` **客户端不再读取**。
> **改它不会切换后端**，改的是上面两个变量或 `BACKENDS` 本身。

### 4.3 确认"我现在在哪个库"

| 方法 | 命令 |
| --- | --- |
| 看 `.env.local` 配的 deployment | `grep CONVEX_DEPLOYMENT .env.local` |
| 打开当前 deployment 的控制台 | `npx convex dashboard` |
| 看前端连的库 | 登录页切换器下方显示的 deployment 主机名 |
| 看某表行数 | `npx convex data <table> --format jsonArray`（dev）／加 `--prod` |

> `npx convex data` 等命令默认作用于 `.env.local` 里 `CONVEX_DEPLOYMENT` 指定的库；
> 加 `--prod` 才作用于生产库。**`npx convex deployment` 没有 `list` 子命令**
> （只有 `select` / `create` / `token` / `usage`），别拿它查当前库。

## 5. 部署

前端与后端是**两个独立部署**：`convex/` 改动不会随 `pages.dev` 生效，反之亦然。

### 5.1 前端 → Cloudflare Pages

```bash
npm run build
wrangler pages deploy dist --project-name=kb-app --branch=main
```

- 配置见 `wrangler.toml`：`name = "kb-app"`、`pages_build_output_dir = "dist"`。
- **SPA 回退规则不在 wrangler.toml**，而在 `public/_redirects`（`/*  /index.html  200`），
  Vite 会原样拷进 `dist/`。
- wrangler 是**全局**安装的；凭证在 `~/Library/Preferences/.wrangler`。

**部署后必须验证**（不要只看 HTTP 200）：

```bash
# 1) 本地产物哈希
ls dist/assets/

# 2) 生产域名是否已切到同一哈希
curl -s "https://kb-app.pages.dev/?t=$RANDOM" | grep -oE 'assets/index-[^"]+\.(js|css)'

# 3) 关键文案核对（示例：确认某次改动真的上线了）
curl -s "https://kb-app.pages.dev/assets/index-<hash>.js" | grep -c "迭代周期"
```

⚠️ 生产域名（`kb-app.pages.dev`）与本次部署的预览域名（`<hash>.kb-app.pages.dev`）**不是一回事**：
前者要等别名切换。若线上仍是旧哈希，等 10 秒重试或强制刷新浏览器。

### 5.2 后端 → Convex

```bash
# dev
npx convex dev --once

# prod —— 强制交互确认
npx convex deploy
```

**非交互环境**（脚本、Agent）下 `npx convex deploy` 会报
`Cannot prompt for input in non-interactive terminals`。需要分配伪终端并把确认喂进去：

```bash
( sleep 6; printf 'y\n'; sleep 90 ) | script -q /dev/null npx convex deploy
```

> ⚠️ **必须 `sleep` 在前**送输入；否则 `y` 会在提示出现前被吃掉，**静默不推送而退出码仍是 0**。

**推送后必须验证**（prod 不会给你错误信息，见 §9）：

```bash
# 一是看部署输出里有没有 "Deployed Convex functions to ..."
# 二是独立确认函数真的更新了：
npx convex function-spec        | grep -A2 '"identifier": "goals.js:createGoal"'
npx convex function-spec --prod | grep -A2 '"identifier": "goals.js:createGoal"'
```

### 5.3 部署顺序规则（重要）

取决于这次改动是**放宽**还是**收紧**校验器：

| 改动性质 | 举例 | 正确顺序 |
| --- | --- | --- |
| 放宽参数（旧客户端仍能用） | `labelId` 由必填改可选 | **先后端，后前端** |
| 收紧参数 | `labelId` 由可选改必填 | **先前端，后后端**（否则旧前端先崩） |
| 前端开始读新返回字段 | `getBoard` 新增 `goalLabels` | **先后端，后前端**（否则读不到） |
| 前端不再传某字段 | 新建卡片不再传 `labelId` | **先后端，后前端** |
| 纯前端 / 纯后端 | 文案、样式 / 内部重构 | 各自部署即可 |

口诀：**先让服务端能接受新旧两种客户端，再更新客户端。**

## 6. 数据导出与导入

### 6.1 全量导出（标准做法）

```bash
bash scripts/backup-deployments.sh          # 加 --files 可连附件一起备份
```

产物：`backups/<时间戳>/{dev,prod}.zip`。脚本会校验归档**非空**，空归档直接 `exit 1`
（避免"以为备份过了"）。

**这就够了吗？** 对结构变更流程够用。但**建议顺手验证一次可恢复性**（见 §11）。

### 6.2 导出物格式

Convex 原生快照，ZIP 内：

```
README.md                       说明
_tables/documents.jsonl         表的注册信息（每行 {"name":"activityLog","id":10001}）
<named>/documents.jsonl         该表的**真实数据**，一行一个文档
<named>/generated_schema.jsonl  该表的 schema
```

> ⚠️ **常见误判**：只看到 `_tables/documents.jsonl` 有十几行就以为"导出有数据"——
> 那只是**表的注册信息**。真实数据在**每个表自己的目录**里。
> 验证备份是否真的抓到数据，要看各表文件大小，例如：
> ```bash
> unzip -l backups/<时间戳>/dev.zip | sort -k1 -n | tail
> ```
> 一个 `sessions/documents.jsonl` 只有 10 字节就说明该表是空的。

### 6.3 恢复 / 导入

```bash
# 整库恢复（⚠️ --replace 是整表覆盖）
npx convex import --replace backups/<时间戳>/dev.zip
npx convex import --prod --replace backups/<时间戳>/prod.zip
```

⚠️ `--replace` 会**丢掉「导出之后」写入的数据**。执行前先确认没有新写入，否则**再导一次**。

**单表导入 / 清空**

```bash
# 读表
npx convex data <table> --format jsonArray

# 用文件整表替换
npx convex import --table <table> --format jsonArray --replace --yes data.json

# 清空单表（传空数组）
printf '[]' > /tmp/empty.json
npx convex import --table <table> --format jsonArray --replace --yes /tmp/empty.json

# prod 加 --prod（⛔ 只允许用于恢复/补数据，禁止用它清库）
```

> `convex import` 是**服务端异步**执行的，命令返回≠数据已可见。脚本 `reset-data.sh`
> 因此会轮询等待，手工操作时请自行复查行数。

### 6.4 按项目/按记录删除（红线 1 的推荐做法）

**不要**为了删掉一条数据而清空整表，优先：

1. **走业务接口**：如删项目用 `projects:deleteProject`（已完整级联 12 张表）。
2. **定向脚本**：按 id 查询、逐个 `ctx.db.delete`。
3. **必要时用单表 `--replace`**，但必须先 `npx convex data` 导出**保留**的行，过滤后再导入。

## 7. 数据表结构变更流程（强制）

适用于 `convex/schema.ts` 的任何改动：加/删表、加/删字段、改字段类型、加/删索引、改枚举。

> ⛔ 禁止用「清空生产库重来」代替迁移。

### 步骤 1 —— 先导出 dev 和 prod（无条件）

```bash
bash scripts/backup-deployments.sh
```

**两个都要导出**：dev 与 prod 是独立数据库，schema 要分别推送，只备份一个，另一个一旦导错无从恢复。
（纯新增字段不需要后续导入，但**导出照做**。）

### 步骤 2 —— 改 schema 并推送到两个 deployment

```bash
npx convex dev --once     # dev
npx convex deploy         # prod（需伪终端确认，见 5.2）
```

纯新增字段/表/索引由 Convex 自动处理；索引在推送后**后台构建**。

### 步骤 3 —— 导入现有数据（仅当需要重建表或改写数据时）

```bash
npx convex import --replace backups/<时间戳>/dev.zip
npx convex import --prod --replace backups/<时间戳>/prod.zip
```

⚠️ 先确认导出之后没有新写入。**纯新增的字段/表不要执行这一步。**

### 步骤 4 —— 验证两个环境

```bash
# dev：错误信息完整，可直接看错误码
npx convex function-spec | grep -A3 '"identifier": "goals.js:createGoal"'

# prod：只能靠"成功返回"判断（错误信息被脱敏，见 §9）
curl -s https://coordinated-camel-303.convex.cloud/api/query \
  -X POST -H 'Content-Type: application/json' \
  -d '{"path":"auth:me","args":{},"format":"json"}'
# 期望：{"status":"success","value":null}
```

### 步骤 5 —— 删字段：必须「先清数据、再删 schema」，且要分三次推送

**这是最容易踩坑的一步，2026-10-13 实删 `goals.description` 时逐条踩过。** Convex 在推送时
**会校验既有文档**，两种报错都会让 `npx convex dev --once` / `convex deploy` 直接失败：

| 时机 | 报错 | 含义 |
| --- | --- | --- |
| schema 已删字段、数据还留着 | `Object contains extra field 'description' that is not in the validator` | 文档有 schema 没声明的字段 |
| schema 里字段是**必填**、却把它 patch 成 `undefined` | `Object is missing the required field 'description'` | patch 掉必填字段 = 文档缺字段 |

所以**不能**「先改 schema 再清数据」（顺序反了），**也**不能「必填字段直接 patch 成 undefined」。
正确顺序是**三次推送**：

```bash
# ① 把字段放宽为 optional（此刻数据仍有该字段，合法）→ 推送
#    仅此一步需要临时改动 schema.ts，用 TEMP-MIGRATION 注释标好，方便回删
npx convex dev --once

# ② 加一个一次性 internalMutation，把数据上的字段 patch 成 undefined → 推送并执行
npx convex dev --once
npx convex run tmpStripFields:run          # 只作用当前（dev）deployment
npx convex data goals --format jsonArray   # 核对：文档里已无该字段

# ③ 从 schema.ts 里彻底删掉字段、并删掉临时函数 → 推送两个环境
npx convex dev --once
( sleep 6; printf 'y\n'; sleep 90 ) | script -q /dev/null npx convex deploy
```

**为什么 `import --replace` 不能替代第 ② 步？** 试过：把导出里的字段删掉再
`npx convex import --table goals --replace`。在**旧 schema 下**会因"缺少必填字段"被拒；
在**新 schema 下**才可行 —— 但新 schema 又推不上去（数据还有该字段）。是个死循环，只能用上面的三步。

> **好消息**：`import --table ... --replace` 是**事务性**的 —— 校验失败时**不会**先清表。
> 实测失败后表里 3 行数据完好无损。
>
> **另一个坑**：`npx convex dev --once` 在**非交互**终端里遇到上述校验失败时可能只挂住不报错
> （看起来像卡死）。看不到输出时改用伪终端跑，错误信息才出得来：
> `script -q /dev/null npx convex dev --once`

**其它迁移先例**：`migrate-label-id.mjs`（`labelName` → `labelId`）、
`migrate-customer-value.mjs`（`storyPoints` → `value`）。两者**都已执行过，勿重跑**。

## 8. 日常运维

### 8.1 首次上线引导（首位注册者即管理员）

系统规则：**第一个注册的账号自动成为管理员**（`isFirstUser`）。因此：

- 新部署想指定管理员 → 让目标账号**第一个注册**。
- 若 `users` 表里已有别人 → 先清空（⚠️ **dev 可用，prod 禁止**，见红线 1）。

### 8.2 清空 dev 数据（仅开发测试）

```bash
bash scripts/reset-data.sh               # 清空 dev 的 15 张表
```

- 脚本会逐表清空并**等到 users 表真的为空**才返回。
- 不带 `--prod` 可用；**带 `--prod` 会被拒绝**，除非显式 `ALLOW_PROD_RESET=1`。
- ⚠️ 现在的 dev 也可能存有真实数据，跑之前先确认或先备份。

### 8.3 卡片类型（两级词表）

| 层级 | 在哪里维护 | 影响 |
| --- | --- | --- |
| 系统级预设 | 管理员 →「卡片类型预设」（`templates.ts`），**按 backlog / sprint 分两套** | 只影响**之后新建**的看板 |
| 看板自有 | 看板内「🏷 卡片类型」按钮（owner 可改） | 只影响本看板 |

**关键规则**：新建看板时按顺序继承 —— ①已有类别则跳过 → ②**同项目、同 kind** 的兄弟看板
→ ③该 kind 的系统预设 → ④内置 `DEFAULT_LABELS`。

> ⚠️ **改已有看板的类别不会自动同步**：系统预设改了只对新建看板生效。
> 若发现某个**迭代看板里只有目标项那几个类别**，说明它的词表是历史上跨 kind 复制来的
> （旧 bug，已修）。处理办法：在看板内「卡片类型」里增删成任务类别，或新建一个迭代看板。

### 8.4 附件与存储

- 上限 20 MB；`isImage` 由服务端按 content type 判定。
- 删除附件时 `ctx.storage.delete` 是 **best-effort**：失败只留下**孤儿 blob**，不影响功能。
- 导出时若要连附件文件一起备份：`bash scripts/backup-deployments.sh --files`。

### 8.5 用户管理

管理员在「用户管理」页可改角色、启停用。规则：

- 不能停用自己（`CANNOT_SUSPEND_SELF`）；
- 系统必须保留 ≥1 名管理员（`LAST_ADMIN`）；
- **停用账号会立即删除其全部会话**（该用户被踢下线）。

### 8.6 查看日志与用量

```bash
npx convex logs                 # 实时跟随当前 deployment 的函数日志（排障首选）
npx convex logs --prod          # 生产库日志
npx convex insights             # 健康度 / 读放大 / OCC 冲突等洞察
npx convex deployment usage     # 当前用量
```

> ⚠️ prod 日志里**函数抛出的错误码会被脱敏**，只能看到 `Server Error` ——
> 要在日志里看到真正的错误码，请在 **dev** 上复现（见 §9）。

### 8.7 活动日志与燃尽图

- 活动日志 13 种事件，随业务操作自动写入。
- 燃尽图是**派生数据**：`scripts/project-snapshot.mjs` **刻意不备份** `burndown`；
  但它**会**被 `backup-deployments.sh` 全量导出。

## 9. 故障排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `wrangler whoami` 报 **Not logged in / token expired** | Cloudflare 凭证过期 | `wrangler login`（浏览器授权） |
| `npx convex deploy` 报 **Cannot prompt for input in non-interactive terminals** | 需要交互确认 | 用 §5.2 的伪终端写法 |
| `npx convex deploy` **退出码 0 但没推送** | `sleep` 不足，`y` 被提前吃掉 | 加大 `sleep`；用 `npx convex function-spec --prod` 确认函数是否真的更新 |
| **prod 上错误信息看不懂**（只有 `Server Error`、没有错误码） | prod 会**脱敏**错误 | 不要用错误文案判断；改到 dev 复现（dev 信息完整），prod 只看"成功返回" |
| prod 上"函数不存在" | 大概率是**误判**（脱敏导致拿文案做判据） | 用 `npx convex function-spec --prod` 确认函数是否存在 |
| 线上还是旧界面 | 别名未切换 / 浏览器缓存 | 核对 bundle 哈希（§5.1），硬刷新 |
| 页面白屏 | 历史遗留的前端异常 | ErrorBoundary 在 Provider 外层，正常应显示错误页；否则看控制台 |
| 新建看板**没有任何类别** | 系统预设为空且无同 kind 兄弟 | 属正常兜底路径；在「卡片类型预设」里补，或确认 `DEFAULT_LABELS` 兜底逻辑未被破坏 |
| **迭代看板里只有目标项类别** | 历史上跨 kind 复制词表（旧 bug） | 见 §8.3 注 |
| 目标项加不进「处理中」列 | **设计如此** | 新目标项只能落在「待处理」（`NEW_GOAL_MUST_BE_PENDING`），进「处理中」要走「排入迭代」 |
| 目标项排在迭代里失败 | 迭代已开始/已结束 | 只能排入**未开始**的迭代（`SPRINT_NOT_PLANNED`），范围冻结是刻意设计 |
| 删标签报错 | 有卡片在引用 / 是最后一个 | `LABEL_IN_USE` / `CANNOT_DELETE_LAST_LABEL` |
| 登录页切换后端后要重新登录 | **设计如此** | 会话只存在于签发它的那个 deployment |
| `reset-data.sh --prod` 被拒绝 | 脚本闸门（红线 1） | 属于预期行为。确需清空请先导出再 `ALLOW_PROD_RESET=1` |
| `typecheck` 报 `noUnusedLocals` | `tsconfig.json` 开启了严格未使用检查 | 删掉未使用的变量/import；**不要**关掉该选项 |

### 9.1 prod 验证的正确姿势

prod **不会**告诉你为什么失败。因此：

```bash
# ✅ 正确：只看是否 success
curl -s https://coordinated-camel-303.convex.cloud/api/query \
  -X POST -H 'Content-Type: application/json' \
  -d '{"path":"auth:me","args":{},"format":"json"}'
# → {"status":"success","value":null}

# ✅ 正确：只读查看线上真实生效的校验器
npx convex function-spec --prod

# ❌ 错误：拿 prod 的错误文案判断"函数不存在/参数不对"
```

## 11. 附录：备份文件格式与恢复演练

### 11.1 怎么判断一个备份"真的有数据"

```bash
TS=2026-10-12T07-39-20            # 换成实际时间戳
unzip -l backups/$TS/dev.zip | sort -k1 -n | tail -20
```

判据：

- 各表目录下的 `documents.jsonl` **字节数 > 10** 才代表有行；
- `_tables/documents.jsonl` 只是**表注册信息**，不能作为"有数据"的依据；
- 若要确认行数，解压后 `wc -l`：

```bash
rm -rf /tmp/bk && mkdir /tmp/bk && cd /tmp/bk
unzip -q /path/to/backups/$TS/dev.zip
for f in */documents.jsonl; do printf "%-32s %s\n" "$f" "$(grep -c . "$f")"; done
```

### 11.2 恢复演练（建议在 dev 或临时 preview 部署上做）

```bash
# 1) 现网导出
bash scripts/backup-deployments.sh

# 2) 记录当前行数
npx convex data projects --format jsonArray | head -c 200

# 3) 恢复
npx convex import --replace backups/<ts>/dev.zip

# 4) 核对恢复结果
npx convex data projects --format jsonArray
npx convex function-spec | head -5      # 函数仍在
```

⚠️ 恢复演练**不要在生产库上直接做**。prod 只允许在**确需恢复**时执行 `import --prod --replace`，
且执行前必须有一次**最新的**导出。
